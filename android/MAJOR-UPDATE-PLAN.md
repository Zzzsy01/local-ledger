# 随手账大版本更新方案

方案日期：2026-10-11；发布日期：2026-10-12。五条首版流程已实现，2.0.0（versionCode 13）已发布至原 GitHub 更新渠道，数据库和完整备份格式仍为 6。验证与交付边界见 [2.0.0 验证记录](verification/2.0.0.md)。

## 更新目标与边界

这轮重点是让已有记录更好用：记账时少重复输入，看报表时能找到原因，安排今天时少在页面之间往返，把需要的数据带出去分析。

用户已经明确排除“预计到账管理”和“账户／资金性质区分”，这轮不加入这些功能，也不以其他名称重新引入。个人收入来源、家庭支持、未来安排等背景仍可在分析对话中说明，不要求在应用里维护个人财务档案。

沿用本地存储、现有双模式导航、现有 Repository 与领域规则。这轮不以新增服务、切换技术栈或重写界面作为前提。用户已授权实施下方五条首版流程；候选功能继续暂缓。

## 开源调研

调研依据为项目官方仓库、README、使用文档与发行说明，未安装这些应用作完整体验测试。下表中“本项目建议”是结合本地代码作出的判断，并非原项目功能的复刻清单。

| 项目与一手来源 | 已确认的做法 | 本项目建议 |
|---|---|---|
| [Cashew 官方仓库](https://github.com/jameskokoska/Cashew)、[使用指南](https://cashewapp.web.app/faq.html) | 交易名称建议及分类关联、灵活预算、搜索筛选、批量选择和可调整的录入步骤 | 借鉴名称建议和少填写的录入流程；保留现有月总预算，先把预算进度讲清楚 |

| [My Expenses 官方仓库](https://github.com/mtotschnig/MyExpenses) | Android 快捷录入、QIF／CSV 数据进出、多条件分析和银行流水核对 | 借鉴快速入口和可移出的数据；我们已有快捷入口、支付 CSV 导入，不把它们再算作新功能 |
| [Loop Habit Tracker 官方仓库](https://github.com/iSoron/uhabits) | 离线习惯记录、历史图表、灵活频次、组件及 CSV／SQLite 导出；习惯进度不因一次漏记全部归零 | 改善现有打卡历史的查看和今日入口；展示实际完成次数，不新增评分公式或强制连续打卡目标 |
| [Super Productivity 官方仓库](https://github.com/super-productivity/super-productivity) | 待办、日程安排、时间记录和专注模式处于同一工作流程 | 从已有待办开始专注，把今天要处理的记录集中显示；不引入它的项目管理和外部平台集成 |
| [Ivy Wallet 官方仓库](https://github.com/Ivy-Apps/ivy-wallet) | 原生 Android 记账与架构参考；仓库明确已停止维护 | 只作为历史参考，不作为新增运行依赖。其架构参考已在本项目文档中使用 |

需要借鉴的是操作路径和展示方式。Cashew 的 Flutter 工程、Actual 与 Super Productivity 的应用结构都不需要移入现有 Kotlin／Compose 工程。本轮没有复制外部实现代码或素材。

## 建议纳入这轮的五条使用流程

### 1. 记账与连续补账

进入记账页先看清金额、分类、账户、日期；商家／用途和备注仍可直接填写，地点、报销等低频内容放入现有表单的更多内容区。日期保持可见，方便补录旧账。

在现有商家字段旁提供来自有效历史交易的名称建议，例如食堂、公交、某个订阅。选择后可带入有效分类与账户，不覆盖用户已明确修改的内容，不自动提交。只使用本地历史，不维护第二套商家数据库或模板表。

新增“保存并继续”：每次保存生成独立 UUID；保存成功才清空金额及本笔文字内容，保留用户正在补账的日期、分类、账户和交易类型。保存失败保留草稿。重复金额、相近时间不能成为自动删除或合并的理由。

既有“再记一笔”继续保留，避免为了新入口改掉已熟悉的操作。

验收：连续补录三笔旧账不必重新打开表单；每笔只写入一次；中途失败仍能修改重试；已停用的分类／账户不会被建议用于新账。

### 2. 从报表找到原因

分类构成中的项目可以点击进入该日期范围、交易类型和分类的明细；趋势中的日期／月份可以打开对应范围的明细。明细的合计、笔数和列表使用同一组条件，返回保留原报表日期和滚动位置。

前十笔排行显示已有商家／用途及备注，避免只看到“餐饮”或“购物”而不清楚是哪一笔。已有搜索可直接用于查找相同用途，不新增强制标签或第二套分类。

当前月展示截至今天的支出与已过自然日的日均；与上月相同进度比较时明确两边的起止日期，遇到短月说明可比较的天数。完整历史月继续按完整月份展示。区间没有数据时不声称“没有消费”或“已经记全”。

验收：图中某分类合计与点开后的明细合计一致；编辑其中一笔后两处一起更新；转账不进入收入／支出报表；查看月中数据时能区分已过天数与整月天数。

### 3. 看懂当月预算

在现有预算卡补充月预算、已记录支出、剩余额度、剩余天数，以及“余下天数日均额度”。支出沿用所选整月的有效流水，包含用户记录在未来日期的账目。当前月剩余天数包含今天，文案明确这一点。例：剩余 700 元、含今天剩余 20 天，日均额度为 35 元。

消费进度和日历进度可以并列显示，帮助用户自己判断节奏。这个数来自已设预算，不命名为“安全可花金额”，也不代表账户里一定有相应现金。超过预算时展示超出金额，不继续显示正向日均额度；未设预算、历史月份和未来月份分别给出符合状态的内容。

预算使用现有实际支出口径。收入、转账不冲抵预算支出，报销标记也不能自动减少已花金额。卡片可进入本月支出明细。不开设预计到账、不增加账户性质、不做九天样本的长期生存预测。

验收：月末、二月、跨年、未设预算和超预算都显示明确结果；隐藏金额时同时隐藏真实预算进度图形。

### 4. 今天要做什么

在备忘录模式的现有主页增加轻量今日区域：到期及逾期的未完成待办、待复习单词数量、进行中的专注，以及今日习惯入口。没有到期日的待办继续留在原清单，不自动推断它们都应今天完成。

从待办点“开始专注”，带入任务名称，复用已有时长选择和专注计时。专注结束后由用户勾选待办完成，不把计时结束当作任务完成。第一版带入的是标题，不建立任务与专注的持久关系，不据此推断任务耗时或计划完成比例。

现有周／月小结中的专注和习惯数字可打开相应记录。无需填写新的学习档案或维护复杂项目树；阅读、学习计划与单词卡保留各自已有入口。

验收：从待办开始计时不必再输入名称；暂停、后台返回、进程重建继续沿用现有计时规则；漏一天打卡不会删除此前历史；切换记账／备忘录仍保留原页面和列表位置。

### 5. 把数据带出去分析

新增“导出财务分析数据”：选择时间范围、预览账目数量和将包含的字段后，由用户保存文件。首版 JSON 包含统计说明、有效流水、相关分类／账户、适用的预算和现有财务固定规则；另提供有效流水 CSV，方便用表格查看。金额仍保存整数分，并明确单位和币种；CSV 处理换行、引号及表格公式前缀等外部使用边界。

分析 JSON 至少说明：导出时间与时区、包含结束日期的范围、收入／支出／转账口径、账目发生时间和实际录入时间、有效流水与有记录日期的数量，以及账户账面余额的计算方式。不能把“有记录的天数”写成“已完整记账的天数”。

账户余额标为导出时的账面余额，其计算依赖账户初始值及全部有效流水，不能只用导出区间内的流水计算。应用当前没有记录初始余额的基准日期，文件如实说明该信息未记录；不能自动声称其是月初或银行卡实际余额。分析工具仍可能需要询问这个背景。

财务导出直接在数据库事务中读取所需表，不调用会读取照片和所有生活记录的完整 `snapshot()`。默认不包含备忘录、日记、单词、物品照片、支付通知原文及已删除流水。导出是用户选择的分享动作，不自动发送给模型或其他服务。

完整备份继续负责全部恢复；分析文件采用独立格式和明确标识，不能作为完整备份恢复。成功导出完整备份后可在现有设置页显示时间，仅表示文件写入成功，不声称文件已安全保存在其他设备上。提醒首版停留在页面提示，不增加后台提醒任务。

验收：分析文件与同口径界面合计一致；转账不造成虚假收入和支出；CSV 可正确读取含逗号、引号和换行的备注；取消或失败不更新备份成功时间；分析导出不会读取或包含生活隐私内容。

上述首版范围可以复用现有业务字段，不需要为了“大版本”升级数据库。导出元信息的结构、短月比较细节和新界面入口需在各自实现阶段完成最终定义，并先搜索现有辅助方法。实现后的测试按实际改动选择，金额／日期计算和财务导出边界保留少量有意义的长期测试，不为文案或布局建立复杂测试环境。

## 暂不纳入的候选

| 候选 | 暂缓理由与重新考虑条件 |
|---|---|
| 分类预算、周预算、任意周期预算 | Cashew 的能力很完整，但我们现有月总预算还能先改善；用户明确需要给某类别／周期设额度后，再定义业务数据与备份兼容 |
| 订阅直接确认记账 | 当前生活订阅只推进续期日期，财务固定账目已有独立确认流程。直接桥接涉及重复确认、账户／分类选择和礼品卡支付周期，需确认真实操作需求后再设计，不默认自动扣款 |
| 拆单、报销到账关联、余额对账 | 有真实混合付款、到账匹配或余额差异案例后再做；不能把本次分析的每个追问都变成数据模型 |
| 保存复杂报表、自定义首页编辑器、标签体系 | 第一版先提供可追到明细的固定报表和轻量今日区域，不要求用户配置工作台 |
| 习惯任意频次、任务与专注持久关联 | 新语义涉及历史统计与迁移；现有打卡、标题预填及统计查看足以完成首版流程 |
| 内置 AI、云同步、服务器、外部平台集成 | 本轮没有这些需求；分析导出可以配合用户已有工具使用 |

## 这轮调研能回答什么

开源参考说明了一些成熟的交互方式，本地代码说明哪些能力可以直接复用。两者支持这份方案的可行性判断，但没有证明每个候选功能都适合用户。

这次经济分析中，账目日期、实际支出、账户计算、订阅相关记录等事实可以通过更清楚的导出和页面表达减少追问。家庭是否提供支持、收入何时实际出现、一次付款买了多久的服务等信息，账本无法可靠推断；应用不应为了假装“全自动分析”而要求用户长期填表。

本方案不写入用户的余额、生活困境、朋友账户或个人备忘录，也没有修改原始备份。
